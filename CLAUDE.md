# AutoQuest

Геймифицированный веб-курс Python «с нуля» для QA-инженера, переходящего в автоматизацию тестирования. Статический сайт, никакого бэкенда и сборки — открывается прямо как `index.html`.

Статус модулей, инфраструктуры и бэклог — **см. `ROADMAP.md` в корне репозитория**, он обновляется отдельно и не дублируется здесь.

## Архитектура

- `index.html` — разметка + подключение стилей/скриптов
- `css/style.css` — все стили
- `js/interpreter.js` — собственный интерпретатор подмножества Python на JS (без Pyodide): токенайзер → рекурсивный спуск → tree-walking executor. Держит все runtime-типы (`PyList`, `PyDict`, `PyFloat`, `PyFunc`), билтины и обработку ошибок с `pyName`/`pyLine`.
- `js/modules-data.js` — контент курса: массив `MODULES` (теория + `tasks` + `homework` на модуль) и общие для всех check-функций хелперы `matchEn`/`deCyr`/`CYR2LAT` (подсказка про русскую раскладку вместо английской). **Важно:** эти хелперы объявлены здесь, а НЕ в `app.js`, потому что `app.js` целиком обёрнут в IIFE — если положить их туда, check-функции модулей (объявленные в отдельном файле, вне этого IIFE) их не увидят. Уже наступали на эти грабли один раз при разбиении файла — не повторять.
- `js/app.js` — состояние, рендер, запуск/проверка задач, редактор кода (номера строк, подсветка синтаксиса и строки с ошибкой, автодополнение). Обёрнут в `(function(){ ... })()`.

Прогресс студента — в `localStorage` браузера (`autoquest-state`, `autoquest-code-*`, `autoquest-reason-*`, `autoquest-signal`), плюс опциональная синхронизация через `claude.use('db')`, если сайт открыт как Claude Artifact (на GitHub Pages этого API нет — код грациозно откатывается на чистый `localStorage`, трогать не нужно).

## Визуальная концепция («The Codebase», 8-битный аркадный стиль)

С 9 сентября 2026 у сайта есть игровая обёртка поверх курса — не референс на конкретную игру (Contra/Battletoads и т.п. пробовали и осознанно отвергли), а originally-придуманный сеттинг: игрок — silhouette-фигура «Debugger» без прорисованного лица (детальные лица/персонажи не получались — решили не рисовать), враги — баги (Infinite Loop, Spaghetti Hydra, KeyError Kraken...), боссы — это реальные `boss:true` задачи курса (никакой отдельной «игровой» механики боя, только косметика вокруг существующей задачи).

- **`#view-title`** — стартовый экран (аркадный HUD, hero-силуэт, выбор Signal Color, NEW GAME/CONTINUE). Показывается первым, `#site-wrap` (path+module) скрыт до клика.
- **Signal Color** — косметический выбор акцентного цвета (mint/amber/violet/cyan), хранится в `autoquest-signal`, применяется через CSS custom properties на всех `.arcade`-элементах (`--a-accent/--a-glow/--a-dim/--a-bg0/--a-bg1/--a-edge`...) — см. `SIGNALS`/`getSignal()`/`setSignal()`/`applySignalEverywhere()` в `app.js`. **Любой новый `.arcade`-элемент обязан иметь и класс `.arcade`, и (там где задаётся вручную) `data-signal` — без класса `.arcade` CSS-переменные темы не резолвятся** (уже наступали на эту ошибку с боссовым хедером).
- **`renderBossHeader()`** — декоративный хедер перед `boss:true`-задачей; **`showVictory()`** — оверлей победы после боя, реальные данные (XP/streak/level/следующий модуль), без наград/лута (осознанно решили не делать пока).
- **`renderBriefing()`** — SYSTEM-реплика гейм-мастера при входе в модуль (кто здесь, сколько испытаний, кто финальный босс), построена из реальных данных модуля, не отдельный написанный текст на модуль.
- **Топбар** — с 9 сентября 2026 аркадный HUD-стрип (`.topbar.arcade .hud`, zero-padded `LV.01`/`0000 XP`/сегментированный XP-бар/🔥streak), НЕ пилюли в стиле JavaRush (первая версия так выглядела — это было явно отвергнуто пользователем и передизайнено).
- Ретема `#view-path`/`#view-module` — только визуальное оформление карточек/фона (см. блоки `#view-path.arcade`/`#view-module.arcade` в `css/style.css`), **не трогает** DOM-структуру/логику `renderPath()`/`openModule()`.
- Редактор кода (`.editor-wrap`/`textarea.editor`/`.editor-gutter`/`.editor-highlight`/`.tok-*`) с 9 сентября 2026 **тоже ретеменирован под аркадную палитру** (фон/бордер/цвета токенов — см. блок `#view-module.arcade .editor-wrap`/`.tok-*` в `css/style.css`), но именно layout/JS-логика (`syncGutter`/`updateHighlight`/scroll-sync) не менялась — только цвета. `.editor-wrap` имеет фиксированную `height:150px` (см. «Известный класс багов» ниже) — это важно не убирать при доработках.

## Известный класс багов: flex-контейнер `.editor-wrap` без явной высоты

`.editor-wrap` — `display:flex;align-items:stretch`. Если убрать `height:150px`, высота контейнера снова начнёт определяться самым высоким ребёнком по natural content size — а `.editor-gutter` (номера строк, `overflow:hidden`, без своей явной высоты) игнорирует `overflow:hidden` при расчёте *intrinsic* размера и «раздувает» всю строку под реальное количество строк кода. Из-за этого `.editor-highlight` (`position:absolute;inset:0` относительно `.editor-code`) рендерился на всю раздутую высоту, не обрезаясь и не скроллясь синхронно с textarea (у которой фиксированная `min-height:150px` + `overflow-y:auto`) — визуально это выглядело как «мусорные» задвоенные цифры под редактором на любой задаче длиннее ~7 строк. Чинится строго явной `height` на `.editor-wrap`, совпадающей с высотой textarea — **если понадобится когда-нибудь сделать textarea растягиваемым (`resize`) или другой высоты, `.editor-wrap` должен получить ту же высоту синхронно через JS, а не оставаться `height:auto`.**

## Известный класс багов: скрытый горизонтальный скроллбар у `textarea.editor` рассинхронизирует высоту с `.editor-gutter`/`.editor-highlight`

Второй, отдельный источник того же визуального симптома («задвоенная»/съехавшая последняя строка внизу скролла), пойманный 9 сентября 2026 уже после фикса выше. У `.editor-wrap textarea.editor` был задан только `overflow-y:auto`, без explicit `overflow-x` — а по спеке CSS, если один из `overflow-x`/`overflow-y` не `visible`, второй, если был `visible`, тоже вычисляется как `auto`. Вместе с `white-space:pre` + `wrap="off"` (нужны, чтобы длинные строки не переносились) это давало textarea собственный **горизонтальный** скроллбар, который отъедает несколько px высоты у *текстового* поля — а `.editor-gutter`/`.editor-highlight` (`overflow:hidden`, никакого скроллбара) этих px не теряют. В результате `textarea.scrollHeight - clientHeight` (максимальный scrollTop) у textarea оказывался на ~13px больше, чем у gutter/highlight — у самого низа скролла реальный код прокручивался дальше, чем номера строк/подсветка физически могли докрутить (их `scrollTop` клэмпился к меньшему максимуму браузером), и три слоя показывали разные строки внизу. Починено явным `overflow-x:hidden` на `.editor-wrap textarea.editor` (см. комментарий в `css/style.css` рядом с правилом) — **если когда-нибудь понадобится горизонтальный скролл длинных строк, придётся синхронизировать ещё и `scrollLeft` между всеми тремя слоями (сейчас синхронизируется только `scrollTop`), а не просто снимать `overflow-x:hidden`.**

После этого фикса оставался ещё остаточный ~2px зазор в максимальном `scrollTop` (textarea против gutter/highlight) — из-за того, что `.editor-wrap` это `border-box` с 1px бордером сверху и снизу, поэтому его flex-stretch-детям (`.editor-gutter`/`.editor-code`, и `.editor-highlight` внутри него через `inset:0`) достаётся content-box высотой 148px, а не 150px, тогда как textarea (не являющаяся flex-ребёнком `.editor-wrap` напрямую, она внутри `.editor-code`) брала `min-height:150px` из базового правила `textarea.editor` и на 2px переполняла свои 148px (обрезалось `overflow:hidden` у `.editor-wrap`). Починено — `.editor-wrap textarea.editor` теперь переопределяет `min-height:148px`, совпадающий с реальной высотой gutter/highlight, а не 150px из базового правила.

## Ограничения интерпретатора (обязательно учитывать при написании новых заданий)

- списки/словари-литералы — **только в одну строку**, перенос скобки на несколько строк ломается с `SyntaxError`
- нет срезов (`x[1:3]`), только одиночный индекс (отрицательный — тоже работает)
- нет общего оператора `in` — только конструкция `for ... in`
- у словаря нет `.items()` — только `.get(key, default)`, `.keys()`, `.values()`
- `min()`/`max()`/`.sort()` — сравнивают только числа (raw `numOf()`), не работают на списках словарей по ключу
- функции: без default-параметров, без `*args`/`**kwargs`, без multiple return / tuple unpacking
- `and`/`or`/`not` есть, но **нет chained comparisons** (`1 < x < 10` не работает — только через `and`)

## Конвенции для нового модуля в `MODULES`

- Объект модуля: `id`, `num`, `phase`, `title`, `desc`, `theory` (массив строк, каждая концепция — с примером попроще И посложнее + зачем это нужно в реальной автоматизации), `tasks` (10 задач), `homework` (3 задачи)
- **Весь текст модуля на английском** (`title`, `goal`, `hint`, `theory`, код в `starter`/`code`) — с 8 сентября 2026 весь курс переведён на английский, русского текста в модулях/UI больше не оставлять
- Задача = `{id, title, goal, hint, starter, check(out){...}}`; предсказание вывода = `{id, title, kind:'predict', goal, hint, code}` (без `check`); финальная задача модуля — `boss:true`
- В `starter` никогда не давать готовое решение — только заготовку/баг для исправления
- `check()` почти всегда сводится к `const m = matchEn(out, 'ожидаемый вывод'); if(m) return m; return {ok:false, msg:'...'};`
- Тема заданий с модуля 4 — сквозной проект AutoQuest (e-commerce на automationexercise.com): корзина, скидки, каталог товаров и т.д.
- С модуля 6 (см. ROADMAP «Модули без браузерной песочницы») задачи вместо обычного кода — `kind:'checklist'` (самостоятельно отмечаемый шаг, опционально `starter` с кодом для показа) или `kind:'predict', offline:true, expected:'...'` (сравнение с заранее known-correct выводом реального CPython, ничего не выполняется в браузере)
- `reasonPrompt:'...'` на fix-задаче — необязательное поле, форсирует ввести текст (не оценивается) перед разблокировкой кнопки Check; используется точечно на паре задач за модуль, не на всех fix-задачах подряд
- Теория — массив строк ИЛИ объектов `{text, examples:[{label:'Simple'|'In practice', kind:'real'(для In practice), code, result}]}` — у каждой концепции должен быть Simple + In practice (automation-контекст) пример, оба реально прогнаны через интерпретатор/python перед публикацией, не посчитаны на бумаге

## Кэш GitHub Pages (важно при каждом пуше, трогающем index.html/css/js)

GitHub Pages ставит `Cache-Control: max-age=600` на все файлы (сам `index.html` тоже) — после пуша браузер может отдавать старую версию до 10 минут, и это не чинится на стороне сервера (Pages не даёт настроить заголовки). Чтобы CSS/JS не залипали независимо от `index.html`, все три `<script>` и `<link rel="stylesheet">` в `index.html` версионируются query-параметром — `js/app.js?v=YYYYMMDDx`. **При каждом пуше, где меняется `app.js`, `interpreter.js`, `modules-data.js` или `style.css`, обязательно бампать `?v=...` у соответствующего тега** (например `20260909a` → `20260909b`), иначе браузер продолжит использовать закэшированную версию файла даже после публикации новой. Сам `index.html` в первые ~10 минут после пуша всё равно может быть отдан из кэша CDN — это ограничение Pages, ничем не лечится, кроме ожидания.

## Локальная проверка перед пушем

`.claude/launch.json` запускает `python -m http.server 8935` — открывается через встроенный Browser-инструмент (`preview_start` с `name:"autoquest-static"`). Полезно проверять DOM/CSS-фиксы **до** пуша и ожидания GitHub Pages (~30-60 сек на build + до 10 мин кэша на `index.html`), особенно структурные вещи (высоты/скролл/flex), которые не видно на глаз без скриншота.

**Скриншоты Browser-инструмента в этой сессии периодически возвращают пустой тёмно-синий кадр** (известный артефакт именно этого инструмента/сессии, не баг сайта) — если это произошло, не считать это признаком реальной проблемы. Перепроверять через `getBoundingClientRect()`/`elementFromPoint()`/`getComputedStyle()`/`get_page_text()` — они стабильно показывают реальное содержимое, даже когда скриншот пустой.
