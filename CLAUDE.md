# AutoQuest

Геймифицированный веб-курс Python «с нуля» для QA-инженера, переходящего в автоматизацию тестирования. Статический сайт, никакого бэкенда и сборки — открывается прямо как `index.html`.

Статус модулей, инфраструктуры и бэклог — **см. `ROADMAP.md` в корне репозитория**, он обновляется отдельно и не дублируется здесь.

## Архитектура

- `index.html` — разметка + подключение стилей/скриптов
- `css/style.css` — все стили
- `js/interpreter.js` — собственный интерпретатор подмножества Python на JS (без Pyodide): токенайзер → рекурсивный спуск → tree-walking executor. Держит все runtime-типы (`PyList`, `PyDict`, `PyFloat`, `PyFunc`), билтины и обработку ошибок с `pyName`/`pyLine`.
- `js/modules-data.js` — контент курса: массив `MODULES` (теория + `tasks` + `homework` на модуль) и общие для всех check-функций хелперы `matchEn`/`deCyr`/`CYR2LAT` (подсказка про русскую раскладку вместо английской). **Важно:** эти хелперы объявлены здесь, а НЕ в `app.js`, потому что `app.js` целиком обёрнут в IIFE — если положить их туда, check-функции модулей (объявленные в отдельном файле, вне этого IIFE) их не увидят. Уже наступали на эти грабли один раз при разбиении файла — не повторять.
- `js/modules-data-ru.js` (9 сентября 2026) — перевод контента модулей на русский, `MODULES_RU[moduleId] = {title, desc, theory:[...], tasks:{taskId:{title,goal,hint,reasonPrompt}}}`. Перевод ПОВЕРХ английского оригинала, не отдельный источник истины — любое отсутствующее поле/модуль просто рендерится на английском (fallback в `mField()`/`taskField()`/`theoryItem()` из `js/i18n.js`). **Статус: переведены все 16 модулей + оба чекпоинта** (9 сентября 2026 — эта строка сама какое-то время неверно утверждала «переведён только m1», хотя на деле были готовы уже m1-m11; расхождение нашёл ручной QA-проход (`/tester`), после чего дотранслировали оставшиеся m12-m16). НЕ переводятся: `starter`/`code` (это код, не текст) и `check()` (логика, плюс её `.msg`-строки — отдельный, пока не сделанный кусок работы, см. ROADMAP.md).
- `js/i18n.js` (9 сентября 2026) — локализация UI-хрома (EN/RU): словарь `I18N.en`/`I18N.ru`, `getLang()`/`setLang()` (`localStorage` ключ `autoquest-lang`, дефолт `en`), `tr(key, vars?)` с `{var}`-подстановкой. **Названо `tr()`, а не `t()`** — `t` уже повсеместно используется в `app.js` как имя локальной переменной «текущая задача» (`renderTaskCard(t,...)`, `bindTask(room,t,m)`, `runCheck(t,m)`...), одноимённая глобальная функция либо затенялась бы, либо (хуже) вызывалась бы как `t('key')`, где `t` на самом деле объект задачи — не функция. Как и `matchEn`/`deCyr`, объявлен вне какой-либо IIFE — доступен и `app.js`, и `modules-data-ru.js`. Здесь же — `mField(m, field)`/`taskField(task, m, field)`/`theoryItem(m, index)` (фоллбэк на английский контент модуля, см. пункт выше) и `phaseName(phase)` (отдельная маленькая карта переводов трёх названий фаз — не через `mField`, потому что `m.phase` также используется как ключ группировки в `renderPath()`, и перевод самого поля сломал бы группировку, как только не все модули одной фазы окажутся переведены).
- `js/app.js` — состояние, рендер, запуск/проверка задач, редактор кода (номера строк, подсветка синтаксиса и строки с ошибкой, автодополнение), переключатель языка (`applyLangEverywhere()`/`initLangSwitch()`). Обёрнут в `(function(){ ... })()`.

Порядок подключения скриптов в `index.html` важен: `i18n.js` → `interpreter.js` → `modules-data.js` → `modules-data-ru.js` → `app.js` (последний, использует всё остальное).

Переключатель языка — `.lang-switch`/`.lang-btn` (EN/RU), живёт и в топбаре (`#lang-switch-top`, всегда виден), и на титульном экране (`#lang-switch-title`, рядом с Signal Color). Статичная разметка (`index.html`) переводится через `[data-i18n]`/`[data-i18n-title]` атрибуты — `applyLangEverywhere()` просто проходит по ним и подставляет `tr(key)` в `textContent`/`title`. Динамический контент (путь, открытый модуль) просто перерисовывается той же функцией рендера ещё раз — она и так каждый раз тянет текст через `tr()`/`mField()`/`taskField()`, второй вызов ничего специально «переводить» не должен. Если меняешь язык, пока открыт модуль — `currentModuleId` (module-level переменная в `app.js`) говорит `applyLangEverywhere()`, какой `openModule()` перевызвать.

Прогресс студента — в `localStorage` браузера (`autoquest-state`, `autoquest-code-*`, `autoquest-reason-*`, `autoquest-signal`, `autoquest-lang`), плюс опциональная синхронизация через `claude.use('db')`, если сайт открыт как Claude Artifact (на GitHub Pages этого API нет — код грациозно откатывается на чистый `localStorage`, трогать не нужно).

## Визуальная концепция («The Codebase», 8-битный аркадный стиль)

С 9 сентября 2026 у сайта есть игровая обёртка поверх курса — не референс на конкретную игру (Contra/Battletoads и т.п. пробовали и осознанно отвергли), а originally-придуманный сеттинг: игрок — silhouette-фигура «Debugger» без прорисованного лица (детальные лица/персонажи не получались — решили не рисовать), враги — баги (Infinite Loop, Spaghetti Hydra, KeyError Kraken...), боссы — это реальные `boss:true` задачи курса (никакой отдельной «игровой» механики боя, только косметика вокруг существующей задачи).

- **`#view-title`** — стартовый экран (аркадный HUD, hero-силуэт, выбор Signal Color, NEW GAME/CONTINUE). Показывается первым, `#site-wrap` (path+module) скрыт до клика.
- **Signal Color** — косметический выбор акцентного цвета (mint/amber/violet/cyan/**rose**, 5-й добавлен 9 сентября 2026), хранится в `autoquest-signal`, применяется через CSS custom properties на всех `.arcade`-элементах (`--a-accent/--a-glow/--a-dim/--a-bg0/--a-bg1/--a-edge`...) — см. `SIGNALS`/`getSignal()`/`setSignal()`/`applySignalEverywhere()` в `app.js`. **Любой новый `.arcade`-элемент обязан иметь и класс `.arcade`, и (там где задаётся вручную) `data-signal` — без класса `.arcade` CSS-переменные темы не резолвятся** (уже наступали на эту ошибку с боссовым хедером).
- **Персонажи** (9 сентября 2026) — у каждого Signal Color теперь свой ИМЕНОВАННЫЙ персонаж, не просто перекраска одного силуэта: Patch/Патч (mint), Trace/Трейс (amber), Null/Нулл (violet), Ping/Пинг (cyan), Byte/Байт (rose) — `CHARACTER_KEYS`/`heroSvgFor()` в `app.js`, имена идут через `tr()` (`charMint`/`charAmber`/... в `i18n.js`), как и остальной UI-хром, а не остаются английскими как контент курса. Все пятеро — вариации ОДНОГО и того же тела/рук/ног (`HERO_BODY_SVG`, без изменений) с разной ГОЛОВОЙ (`HERO_HEADS[signal]`): капюшон+два глаза (Patch), тот же капюшон+визор-полоса (Trace), гранёная шестиугольная голова (Null), капюшон+антенна (Ping), маленькая скруглённая голова с одним глазом-циклопом (Byte) — сознательно варьируется только голова, чтобы все пятеро читались одной командой, а не разнородными дизайнами (проект уже отверг детальную прорисовку персонажей — см. ниже). `heroSvgFor(signal)` — единая точка правды, используется во всех 3 местах, где раньше был статический `HERO_SVG`: титульный экран (`#title-hero-svg`, изначально пустой `<svg>` в `index.html`, заполняется JS), декорация на странице пути (`#path-hero-svg`, тот же приём), боссовый хедер (`renderBossHeader`, генерируется всегда заново). `applySignalEverywhere()` перерисовывает первые два при смене цвета; третий не нуждается — рендерится с нуля при каждом открытии модуля.
- **Повергнутый босс** (`renderBossVisual(moduleId, defeated)`, 9 сентября 2026) — когда `state.completed[bossTaskId]` истинно, тот же силуэт босса рисуется повёрнутым набок (`transform="rotate(65 100 100) scale(1,0.65)"`), с крестиками вместо глаз и пониженной непрозрачностью — не новый арт на каждого босса, чисто трансформация уже сгенерированного. Применяется в двух местах: превью на карточке модуля в пути (класс `.node-boss.defeated`) и в самом `renderBossHeader` (там же тег меняется на «BOSS DEFEATED»/«БОСС ПОВЕРЖЕН», health-бар — на 4% вместо декоративных 68%). **Важно:** `runCheck()`/`runPredictCheck()`/чеклист-обработчик в `bindTask` патчат только конкретную карточку задачи, не всю комнату — без отдельного вызова `refreshBossHeader(t, m)` сразу после `markDone`, боссовый хедер показывал бы старую («не повержен») позу, пока пользователь не выйдет из модуля и не зайдёт заново. `refreshBossHeader` вызывается в паре с `showVictory(t, m)` во всех трёх местах, где та вызывается — хедер обновляется, пока ещё виден оверлей победы, не только после его закрытия.
- **`renderBossHeader()`** — декоративный хедер перед `boss:true`-задачей; **`showVictory()`** — оверлей победы после боя, реальные данные (XP/streak/level/следующий модуль), без наград/лута (осознанно решили не делать пока).
- **`renderBossVisual(moduleId)`** (9 сентября 2026) — раньше у всех 16 боссов был один и тот же жёстко закодированный SVG-силуэт (нашли на QA-проходе). Вместо 16 отдельно нарисованных монстров (дорого, и проект уже пробовал и отверг детальную прорисовку персонажей/лиц — см. «Визуальная концепция» ниже) — детерминированный генератор: `BOSS_LOOK[moduleId]` задаёт число зубцов/изрезанность/поворот зубчатого силуэта (`bossBlobPath`) + паттерн «глаз» (`BOSS_EYE_PATTERNS`: pair/triangle/row/single/none) + опциональный тематический акцент (`accent`: `cursor` — мигающий курсор вместо рта для модуля про окружение, `crosshair` — прицел для локаторов/Selenium, `stack` — три «цилиндра» для баз данных, `strings` — нити марионетки для Playwright, `twin` — полупрозрачный двойник для моков/стабов, `spiral` — спираль в зрачке для циклов/генераторов). Сид — хэш `moduleId`, так что силуэт стабилен между перерисовками/языками, не рандомный при каждом рендере. Переиспользуется в двух местах: `renderBossHeader()` (полный размер) и `renderPath()` (маленькое превью на карточке модуля, третья колонка `.node`).

## Урок про «пустое место у боссов» (9 сентября 2026) — измерять ГДЕ именно пусто, не только относительно родителя

Пользователь трижды присылал один и тот же тип жалобы («у босса пусто справа») на один и тот же визуальный элемент, и первые два фикса (`.boss-header .arcade-screen{max-width: none→900px→560px}`) были технически верны и подтверждены строгими измерениями (`getBoundingClientRect`, `fetch` продакшен-CSS с `cache:'no-store'`, чистый `localStorage` + force-reload) — сама карточка боссa действительно была ровно по размеру и идеально отцентрована. Проблема была в том, что все эти измерения проверяли **не ту границу**: расстояние карточки от краёв комнаты, а не расстояние содержимого (`.boss-arena` — ряд иконок героя+босса) от краёв самой карточки. Настоящая пустота была ВНУТРИ уже правильно узкой карточки — `.boss-arena` растягивается на всю её ширину (это нормально, это флекс-контейнер), но сами иконки внутри него, без `justify-content`, по умолчанию прижаты влево, оставляя пустоту одним куском справа. Снаружи высокоуровневые измерения (ширина/центрирование карточки) были идеальны, поэтому не показывали проблему — она была на уровень глубже. **Если пользователь показывает скриншот с пустым местом и присланный ранее фикс «не помог» — прежде чем трогать внешний контейнер ещё раз, измерить, где именно проходит граница пустой области: считать отступы КАЖДОГО вложенного уровня (карточка → внутренний ряд → сами иконки), а не только «эта штука относительно родителя».**
- **`renderBriefing()`** — SYSTEM-реплика гейм-мастера при входе в модуль (кто здесь, сколько испытаний, кто финальный босс), построена из реальных данных модуля, не отдельный написанный текст на модуль.
- **Топбар** — с 9 сентября 2026 аркадный HUD-стрип (`.topbar.arcade .hud`, zero-padded `LV.01`/`0000 XP`/сегментированный XP-бар/🔥streak), НЕ пилюли в стиле JavaRush (первая версия так выглядела — это было явно отвергнуто пользователем и передизайнено).
- Ретема `#view-path`/`#view-module` — только визуальное оформление карточек/фона (см. блоки `#view-path.arcade`/`#view-module.arcade` в `css/style.css`), **не трогает** DOM-структуру/логику `renderPath()`/`openModule()`.
- **Боковые поля `#view-path`/`#view-module` на широких экранах — решено НЕ декорировать** (9 сентября 2026). Пробовали `.cab-rail`: декоративные боковые панели с circuit-trace SVG-паттерном (сначала узкие и редкие — жаловались, что дальше них до края окна голая чернота; расширили до реального края `.wrap` и сделали паттерн плотнее — пользователь всё равно оценил результат как «ужас») — **откачено полностью**, кода `.cab-rail` в проекте больше нет. Решили вместо декора расширить сам `.wrap` — `max-width` поднят с 920px до 1180px (см. следующий пункт), пустое место просто перестало быть таким большим. Если тема боковых полей всплывёт снова — не предлагать декоративные рейлы повторно, это уже пробовали.
- **`.wrap`/`.topbar-inner` `max-width:1180px`** (было `920px`, поднято 9 сентября 2026 вместе с откатом `.cab-rail` выше) — общая ширина колонки контента и топбара, держать оба значения синхронными (шапка должна визуально совпадать по краям с контентом под ней).
- Редактор кода (`.editor-wrap`/`textarea.editor`/`.editor-gutter`/`.editor-highlight`/`.tok-*`) с 9 сентября 2026 **тоже ретеменирован под аркадную палитру** (фон/бордер/цвета токенов + скроллбар самой textarea через `scrollbar-color`/`::-webkit-scrollbar-*` — см. блок `#view-module.arcade .editor-wrap`/`.tok-*` в `css/style.css`), но именно layout/JS-логика (`syncGutter`/`updateHighlight`/scroll-sync) не менялась — только цвета. `.editor-wrap` имеет фиксированную `height:150px` (см. «Известный класс багов» ниже) — это важно не убирать при доработках.

## Известный класс багов: flex-контейнер `.editor-wrap` без явной высоты

`.editor-wrap` — `display:flex;align-items:stretch`. Если убрать `height:150px`, высота контейнера снова начнёт определяться самым высоким ребёнком по natural content size — а `.editor-gutter` (номера строк, `overflow:hidden`, без своей явной высоты) игнорирует `overflow:hidden` при расчёте *intrinsic* размера и «раздувает» всю строку под реальное количество строк кода. Из-за этого `.editor-highlight` (`position:absolute;inset:0` относительно `.editor-code`) рендерился на всю раздутую высоту, не обрезаясь и не скроллясь синхронно с textarea (у которой фиксированная `min-height:150px` + `overflow-y:auto`) — визуально это выглядело как «мусорные» задвоенные цифры под редактором на любой задаче длиннее ~7 строк. Чинится строго явной `height` на `.editor-wrap`, совпадающей с высотой textarea — **если понадобится когда-нибудь сделать textarea растягиваемым (`resize`) или другой высоты, `.editor-wrap` должен получить ту же высоту синхронно через JS, а не оставаться `height:auto`.**

Это и понадобилось (9 сентября 2026) — `.editor-wrap textarea.editor` теперь `resize:vertical`. Синхронизация сделана не отдельным механизмом, а расширением уже существующего per-frame rAF-цикла в `bindTask` (`pollEditorScroll`, тот же, что копирует `scrollTop` для скролл-фикса выше): каждый кадр он ещё копирует `editor.offsetHeight` на `wrap.style.height`. Поскольку `.editor-gutter`/`.editor-code` — flex-дети `.editor-wrap` с `align-items:stretch`, а `.editor-highlight` — `position:absolute;inset:0` внутри `.editor-code`, синхронизации одной только высоты `.editor-wrap` достаточно — gutter/highlight подстраиваются под неё автоматически, отдельно их высоту трогать не нужно.

## Настоящая причина рассинхрона gutter/highlight с пустыми строками в конце (9 сентября 2026) — не тайминг

После нескольких заходов на «тайминг scrollTop» (rAF-опрос и т.д. — см. пункты выше) баг всё равно воспроизводился, и пользователь сообщил ключевую деталь: именно при пустых строках В КОНЦЕ кода. Реальная причина оказалась не в синхронизации scrollTop вовсе, а в том, что у `.editor-gutter` и `.editor-highlight` физически РАЗНЫЙ `scrollHeight` для одного и того же количества строк. `renderHighlight()` склеивал строки через литеральные `\n` в один текстовый узел внутри `<pre>`; когда `code` заканчивается переносом строки (частый случай — не только явно пустые строки, а и просто позиция каретки после `Enter` в конце), `code.split('\n')` даёт финальный пустой элемент, и этот пустой «хвост», будучи последним куском текста перед концом `<pre>`, не получает собственной строки по высоте в браузере — `.editor-highlight` рендерился на одну строку (~21.6px) короче, чем `.editor-gutter` (обычный текст, где `syncGutter()` НИКОГДА не добавляет хвостовой `\n`) и сама textarea. Проверено программно (`gutter.scrollHeight` vs `hl.scrollHeight` до фикса: 218 vs 197 для одного и того же 9-строчного кода) — это была настоящая, стабильно воспроизводимая разница в размере, а не гонка по времени, поэтому никакой rAF-опрос scrollTop её не решал.

Исправлено структурно в `renderHighlight()` (`js/app.js`): каждая строка теперь — отдельный блочный `<div class="hl-line">` (пустая строка рендерится как `&nbsp;`, не как пустая строка между `\n`), а не текст, склеенный через `join('\n')`. Блочный `<div>`, в отличие от текстового узла внутри `<pre>`, не может «не получить» строку по высоте независимо от того, чем заканчивается контент — гарантированно N строк текста дают ровно N div'ов ровно той же высоты, что и N строк в `.editor-gutter`. Проверено на 6 разных кейсах (одиночный/двойной хвостовой `\n`, много хвостовых пустых строк, без хвостового `\n` вовсе, пустой код) — во всех `gutter.scrollHeight === hl.scrollHeight`.

## Известный класс багов: скрытый горизонтальный скроллбар у `textarea.editor` рассинхронизирует высоту с `.editor-gutter`/`.editor-highlight`

Второй, отдельный источник того же визуального симптома («задвоенная»/съехавшая последняя строка внизу скролла), пойманный 9 сентября 2026 уже после фикса выше. У `.editor-wrap textarea.editor` был задан только `overflow-y:auto`, без explicit `overflow-x` — а по спеке CSS, если один из `overflow-x`/`overflow-y` не `visible`, второй, если был `visible`, тоже вычисляется как `auto`. Вместе с `white-space:pre` + `wrap="off"` (нужны, чтобы длинные строки не переносились) это давало textarea собственный **горизонтальный** скроллбар, который отъедает несколько px высоты у *текстового* поля — а `.editor-gutter`/`.editor-highlight` (`overflow:hidden`, никакого скроллбара) этих px не теряют. В результате `textarea.scrollHeight - clientHeight` (максимальный scrollTop) у textarea оказывался на ~13px больше, чем у gutter/highlight — у самого низа скролла реальный код прокручивался дальше, чем номера строк/подсветка физически могли докрутить (их `scrollTop` клэмпился к меньшему максимуму браузером), и три слоя показывали разные строки внизу. Починено явным `overflow-x:hidden` на `.editor-wrap textarea.editor` (см. комментарий в `css/style.css` рядом с правилом) — **если когда-нибудь понадобится горизонтальный скролл длинных строк, придётся синхронизировать ещё и `scrollLeft` между всеми тремя слоями (сейчас синхронизируется только `scrollTop`), а не просто снимать `overflow-x:hidden`.**

После этого фикса оставался ещё остаточный ~2px зазор в максимальном `scrollTop` (textarea против gutter/highlight) — из-за того, что `.editor-wrap` это `border-box` с 1px бордером сверху и снизу, поэтому его flex-stretch-детям (`.editor-gutter`/`.editor-code`, и `.editor-highlight` внутри него через `inset:0`) достаётся content-box высотой 148px, а не 150px, тогда как textarea (не являющаяся flex-ребёнком `.editor-wrap` напрямую, она внутри `.editor-code`) брала `min-height:150px` из базового правила `textarea.editor` и на 2px переполняла свои 148px (обрезалось `overflow:hidden` у `.editor-wrap`). Починено — `.editor-wrap textarea.editor` теперь переопределяет `min-height:148px`, совпадающий с реальной высотой gutter/highlight, а не 150px из базового правила.

Третий, отдельный источник того же симптома — уже не постоянный сдвиг, а рассинхрон именно **во время** живого перетаскивания мышью нативного скроллбара textarea (пользователь воспроизвёл руками и записал видео — `gutter`/`hl` заметно отстают от textarea в процессе перетаскивания, хотя после отпускания снова совпадают идеально). Причина: `gutter.scrollTop`/`hl.scrollTop` копировались только по событию `scroll` на textarea, а это событие идёт с главного потока и может коалесцироваться/тротлиться при быстром нативном drag'е скроллбара, тогда как сам textarea перерисовывается на композиторе каждый кадр.

Первая попытка чинить это (rAF-опрос только в окне `mousedown`→`mouseup`) не помогла — пользователь воспроизвёл баг повторно уже на задеплоенной версии с этим фиксом. Окончательное решение: убрать зависимость от событий вообще. `gutter.scrollTop`/`hl.scrollTop` теперь **безусловно** копируются из `editor.scrollTop` на каждом `requestAnimationFrame`, постоянно, пока редактор конкретной задачи не удалён из DOM (проверка `editor.isConnected` внутри цикла — самоостанавливается, не крутится вхолостую вечно). Раз копирование не привязано ни к какому событию, а просто перечитывает текущее значение каждый кадр — рассинхрону физически неоткуда взяться, независимо от троттлинга `scroll`-события. Логика проверена синтетически (0 расхождений за 80 тиков хаотичного изменения `scrollTop` между опросами) — сам `requestAnimationFrame` в Browser-инструменте этой сессии живьём проверить не вышло (окружение не рендерит кадры, тот же артефакт, что и с пустыми скриншотами), но механизм не зависит от кадровой частоты, только от факта регулярного опроса.

## Ограничения интерпретатора (обязательно учитывать при написании новых заданий)

- списки/словари-литералы — **только в одну строку**, перенос скобки на несколько строк ломается с `SyntaxError`
- нет срезов (`x[1:3]`), только одиночный индекс (отрицательный — тоже работает)
- нет общего оператора `in` — только конструкция `for ... in`
- у словаря нет `.items()` — только `.get(key, default)`, `.keys()`, `.values()`
- `min()`/`max()`/`.sort()` — сравнивают только числа (raw `numOf()`), не работают на списках словарей по ключу
- функции: без default-параметров, без `*args`/`**kwargs`, без multiple return / tuple unpacking
- `and`/`or`/`not` есть, но **нет chained comparisons** (`1 < x < 10` не работает — только через `and`)

## Кэш GitHub Pages (важно при каждом пуше, трогающем index.html/css/js)

GitHub Pages ставит `Cache-Control: max-age=600` на все файлы (сам `index.html` тоже) — после пуша браузер может отдавать старую версию до 10 минут, и это не чинится на стороне сервера (Pages не даёт настроить заголовки). Чтобы CSS/JS не залипали независимо от `index.html`, все `<script>` и `<link rel="stylesheet">` в `index.html` версионируются query-параметром — `js/app.js?v=YYYYMMDDx`. **При каждом пуше, где меняется `app.js`, `interpreter.js`, `modules-data.js`, `modules-data-ru.js`, `i18n.js` или `style.css`, обязательно бампать `?v=...` у соответствующего тега** (например `20260909a` → `20260909b`), иначе браузер продолжит использовать закэшированную версию файла даже после публикации новой. Сам `index.html` в первые ~10 минут после пуша всё равно может быть отдан из кэша CDN — это ограничение Pages, ничем не лечится, кроме ожидания.

`.claude/launch.json` запускает `python -m http.server 8935` — открывается через встроенный Browser-инструмент (`preview_start` с `name:"autoquest-static"`). Перепроверять через `getBoundingClientRect()`/`elementFromPoint()`/`getComputedStyle()`/`get_page_text()` — они стабильно показывают реальное содержимое, даже когда скриншот пустой.
