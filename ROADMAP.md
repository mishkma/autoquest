## Платформа

- Структура: `index.html` + `css/style.css` + `js/interpreter.js` (свой Python-движок на JS, без Pyodide) + `js/modules-data.js` (контент модулей) + `js/app.js` (UI/состояние)
- Прогресс студента хранится в `localStorage` браузера (ключ `autoquest-state`)
- Тема сквозного проекта (AutoQuest Test Framework) — с модуля 4, реальный репозиторий/git/CI — с модуля 6+

### Ограничения интерпретатора (важно при написании новых заданий)

- списки/словари-литералы — только в одну строку, без переноса
- нет срезов (`x[1:3]`), только одиночный индекс (в т.ч. отрицательный)
- нет общего `in`, только `for ... in`
- у словаря нет `.items()` — только `.get()/.keys()/.values()`
- `min/max/.sort()` — только по числам
- функции без default-параметров, `*args`/`**kwargs`, multiple return
- **нет `class`, `import`, `try`/`except`** — модули 6+ (ООП, стандартная библиотека, pytest, exception handling и всё последующее, где нужен requests/Selenium и т.д.) целиком идут в реальном Python (см. ниже), не в браузерной песочнице

### Модули без браузерной песочницы (М6+)

С модуля 6 студент ставит настоящий Python и работает в VS Code — песочница дальше не используется вообще, потому что не поддерживает `class`/`import` (нужны для ООП, стандартной библиотеки, pytest, requests, Selenium и т.д.). Вместо `check(out)` там два типа задач:
- **`kind:'checklist'`** — самостоятельно отмечаемый шаг на своей машине (поставил/запустил/закоммитил); опционально показывает код через `starter`, если его нужно ввести/скопировать
- **`kind:'predict', offline:true, expected:'...'`** — то же самое, что обычный `kind:'predict'`, но ничего не выполняется в браузере (сравнение идёт с заранее known-correct выводом настоящего CPython, не с рантаймом песочницы)

Оба типа уже реализованы в `js/app.js`. Весь новый код для таких модулей перед публикацией стоит реально прогонять через `python` (или наш `js/interpreter.js` для обычных модулей) — не считать «на бумаге».

**М14 (Selenium)**: навигация/чтение (`get`, `find_element(s)`, `.text`, `.get_attribute`, `NoSuchElementException`) реально прогнаны через настоящий Chrome против живого automationexercise.com. `.click()`/`.send_keys()` в этой конкретной песочнице (Claude Code sandbox) не работают — синтетический ввод через WebDriver блокируется на уровне окружения (подтверждено: JS-манипуляция DOM работает, `.click()`/`.send_keys()` — нет), это ограничение именно этой изолированной среды, не сайта и не кода. У реального пользователя на обычной машине эти вызовы работают штатно — это стандартный, учебниковый Selenium API, просто не был лично прогнан построчно в этой сессии.

**М15 (Playwright)**: в отличие от М14, здесь `.click()`/`.fill()` реально сработали в этой же песочнице (другой механизм синтетического ввода) — весь модуль, включая полный флоу поиска и `expect().to_have_text()`, прогнан end-to-end против живого сайта. Заодно нашли настоящую живую особенность сайта (не выдумка): cookie-consent баннер реально перехватывает клики (`intercepts pointer events`) на свежей странице — это стало отдельным заданием (т8) вместо того, чтобы быть незамеченным препятствием.

**М16 (архитектура фреймворка)**: финальный/капстоун-модуль собран и прогнан как реальный мини-проект — `pages/products_page.py` + `conftest.py` (yield-фикстура) + `tests/test_search.py` (Playwright) + `tests/test_api.py` (requests), всё вместе через один `pytest -v` из корня проекта. Порядок setup/teardown у yield-фикстуры и поведение `scope="module"` (setup один раз на файл, а не на тест) — оба подтверждены реальным прогоном с `-s`.
