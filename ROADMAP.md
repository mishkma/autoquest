## Платформа

- Структура: `index.html` + `css/style.css` + `js/interpreter.js` (свой Python-движок на JS, без Pyodide) + `js/modules-data.js` (контент модулей) + `js/app.js` (UI/состояние)
- Прогресс студента хранится в `localStorage` браузера (ключ `autoquest-state`)
- Тема сквозного проекта (AutoQuest Test Framework) — с модуля 4, реальный репозиторий/git/CI — с модуля 6+

### Ограничения интерпретатора (важно при написании новых заданий)

- списки/словари-литералы — только в одну строку, без переноса
- нет срезов (`x[1:3]`), только одиночный индекс (в т.ч. отрицательный)
- нет общего `in`, только `for ... in`
- у словаря нет `.items()` — только `.get()/.keys()/.values()`
- `min/max/.sort()` — только по числам
- функции без default-параметров, `*args`/`**kwargs`, multiple return
- **нет `class`, `import`, `try`/`except`** — модули 6+ (ООП, стандартная библиотека, pytest, exception handling и всё последующее, где нужен requests/Selenium и т.д.) целиком идут в реальном Python (см. ниже), не в браузерной песочнице

### Модули без браузерной песочницы (М6+)

С модуля 6 студент ставит настоящий Python и работает в VS Code — песочница дальше не используется вообще, потому что не поддерживает `class`/`import` (нужны для ООП, стандартной библиотеки, pytest, requests, Selenium и т.д.). Вместо `check(out)` там два типа задач:
- **`kind:'checklist'`** — самостоятельно отмечаемый шаг на своей машине (поставил/запустил/закоммитил); опционально показывает код через `starter`, если его нужно ввести/скопировать
- **`kind:'predict', offline:true, expected:'...'`** — то же самое, что обычный `kind:'predict'`, но ничего не выполняется в браузере (сравнение идёт с заранее known-correct выводом настоящего CPython, не с рантаймом песочницы)

Оба типа уже реализованы в `js/app.js`. Весь новый код для таких модулей перед публикацией стоит реально прогонять через `python` (или наш `js/interpreter.js` для обычных модулей) — не считать «на бумаге».

**М14 (Selenium)**: навигация/чтение (`get`, `find_element(s)`, `.text`, `.get_attribute`, `NoSuchElementException`) реально прогнаны через настоящий Chrome против живого automationexercise.com. `.click()`/`.send_keys()` в этой конкретной песочнице (Claude Code sandbox) не работают — синтетический ввод через WebDriver блокируется на уровне окружения (подтверждено: JS-манипуляция DOM работает, `.click()`/`.send_keys()` — нет), это ограничение именно этой изолированной среды, не сайта и не кода. У реального пользователя на обычной машине эти вызовы работают штатно — это стандартный, учебниковый Selenium API, просто не был лично прогнан построчно в этой сессии.

**М15 (Playwright)**: в отличие от М14, здесь `.click()`/`.fill()` реально сработали в этой же песочнице (другой механизм синтетического ввода) — весь модуль, включая полный флоу поиска и `expect().to_have_text()`, прогнан end-to-end против живого сайта. Заодно нашли настоящую живую особенность сайта (не выдумка): cookie-consent баннер реально перехватывает клики (`intercepts pointer events`) на свежей странице — это стало отдельным заданием (т8) вместо того, чтобы быть незамеченным препятствием.

**М16 (архитектура фреймворка)**: финальный/капстоун-модуль собран и прогнан как реальный мини-проект — `pages/products_page.py` + `conftest.py` (yield-фикстура) + `tests/test_search.py` (Playwright) + `tests/test_api.py` (requests), всё вместе через один `pytest -v` из корня проекта. Порядок setup/teardown у yield-фикстуры и поведение `scope="module"` (setup один раз на файл, а не на тест) — оба подтверждены реальным прогоном с `-s`.

Детерминированный генератор зубчатого силуэта (число зубцов/изрезанность/поворот + паттерн «глаз» + опциональный тематический акцент — мигающий курсор для окружения, прицел для локаторов, «цилиндры» для баз данных, нити марионетки для Playwright, двойник для моков, спираль для циклов/генераторов), сид от `moduleId` — стабильно между перерисовками. Проверено на все 16 модулей — каждый даёт свой уникальный path, чекпоинты корректно без босса.
  - **✅ Визуальный полиш боссов, три итерации за один вечер** (9 сентября 2026, запрос пользователя: «боссов тоже наверное покрасивее нужно оформить»):
    - **Итерация 1 (откачена по факту, не по коду — обе идеи ниже её заменили)**: `bossBlobPath` раньше соединял зубчатые вершины прямыми линиями — читалось как случайный зигзаг. Первая попытка провела через те же точки квадратичные кривые (вершина = control point, не точка на линии — стандартный приём «блоб»-силуэта) + добавила радиальную заливку-градиент вместо полой обводки + мягкое гало вокруг глаз. Пользователь сразу же отверг результат: «ужасные дизайны.. просто круги». Причина глубже, чем сглаживание — у большинства боссов radius-jitter вокруг окружности был небольшим (`.03`-`.15`), так что вершины и ДО сглаживания были почти круговыми; сглаживание только добило то немногое, что от «зубцов» оставалось.
    - **Итерация 2 (форма)**: `bossBlobPath` переписан с нуля как настоящая звезда/корона — чередующиеся ВНЕШНИЕ (кончик шипа) и ВНУТРЕННИЕ (вогнутая выемка) вершины, прямые `L`-сегменты между ними (кривая через кончик шипа обратно скруглила бы его в тот же «блоб») + небольшой угловой шум поверх радиального jitter, чтобы шипы не выглядели идеально правильной звездой. Новое поле `inner` на каждый `BOSS_LOOK[moduleId]` — отношение внутреннего радиуса к внешнему — низкое (`.28`-`.4`) даёт острую «нинздя-звезду», высокое (`.6`-`.72`) — шестерёнку/кристалл. Заодно добавлены `BOSS_MOUTH_PATTERNS` (`fangs`/`fang1`/`grin`/`frown`/`none`) — по запросу «мордочки какие-нибудь интересные придумай», чтобы лицо было не только парой глаз.
    - **Итерация 3 (состояние «повержен»)**: пользователь уточнил, что просто наклон+общее затемнение силуэта (см. запись выше про сам факт добавления `defeated`) не читается как «сломан» — «поломанным чтобы был.. трещина чтобы была». Добавлена новая функция `crackLines(seed, count)` — 4 сидированных зигзаг-линии («трещины») от центра к краю силуэта, плюс отдельная градация цвета для повержённого состояния: живой босс — светло-коралловое ядро → тёмно-бордовый край (та же красная «вражеская» палитра), повержённый — светло-серое ядро → почти чёрный край (`#8a8681`→`#1c1a17`), обводка тоже становится серой, X-глаза серые вместо красных. И CSS-glow вокруг силуэта (`.boss-ring`/`.node-boss`) свой на каждое состояние — тёплый красный для живого, нейтральный серый для повержённого (раньше был один и тот же красный glow всегда, из-за чего сломанный серый труп всё равно «светился жизнью»). Убран отдельный `saturate()`-фильтр в CSS — теперь ставший ненужным, раз цвет уже серый в самом SVG.
    - `id` градиента уникален на силуэт+статус (`bossGrad-${moduleId}${defeated?'-d':''}`) — на `#view-path` одновременно на экране до 16 таких `<svg>`, общий `id` заставил бы их все ссылаться на первый попавшийся `<radialGradient>` в DOM. Проверено на каждой итерации: 16 уникальных id, живое/повержённое состояние обе используют верную палитру/трещины/глаза, mobile 375px без переполнения, консоль чистая, локально и на проде.
  - **✅ Превью босса на карточке модуля в пути** (`renderPath`, 9 сентября 2026) — маленькая версия того же `renderBossVisual(m.id)` теперь показывается справа на каждой карточке модуля в `#view-path` (третья колонка грида `.node`, `56px 1fr 64px`), заблёклая/чёрно-белая для ещё не открытых модулей.   - **✅ Побеждённый босс визуально отличается от ещё не пройденного** (`renderBossVisual(moduleId, defeated)`, 9 сентября 2026) — реализован первый из двух вариантов, обсуждавшихся в этом пункте (сам силуэт босса выглядит иначе, а не сцена «герой побеждает босса»): при `state.completed[bossTaskId] === true` тот же детерминированный силуэт рисуется повёрнутым набок (`transform="rotate(65 100 100) scale(1,0.65)"`, `opacity:.55`), с крестиками вместо глаз, плюс приглушение через CSS (`.node-boss.defeated{opacity:.6} .node-boss.defeated svg{filter:drop-shadow(...) saturate(.6)}`). Пользователь продолжал видеть пустоту, потому что настоящая причина была ВНУТРИ уже правильно узкой карточки: `.boss-arena` (ряд с иконками героя+босса) сам по себе занимает всю ширину карточки, но её содержимое (`.boss-hero`+`.boss-ring`, флекс без `justify-content`) прижато влево — вправо от иконок оставалось ~320px пустоты внутри той же рамки.
