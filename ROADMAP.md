## Платформа

- Структура: `index.html` + `css/style.css` + `js/interpreter.js` (свой Python-движок на JS, без Pyodide) + `js/modules-data.js` (контент модулей) + `js/app.js` (UI/состояние)
- Прогресс студента хранится в `localStorage` браузера (ключ `autoquest-state`)
- Тема сквозного проекта (AutoQuest Test Framework) — с модуля 4, реальный репозиторий/git/CI — с модуля 6+

### Ограничения интерпретатора (важно при написании новых заданий)

- списки/словари-литералы — только в одну строку, без переноса
- нет срезов (`x[1:3]`), только одиночный индекс (в т.ч. отрицательный)
- нет общего `in`, только `for ... in`
- у словаря нет `.items()` — только `.get()/.keys()/.values()`
- `min/max/.sort()` — только по числам
- функции без default-параметров, `*args`/`**kwargs`, multiple return
- **нет `class`, `import`, `try`/`except`** — модули 6+ (ООП, стандартная библиотека, pytest, exception handling и всё последующее, где нужен requests/Selenium и т.д.) целиком идут в реальном Python (см. ниже), не в браузерной песочнице

### Модули без браузерной песочницы (М6+)

С модуля 6 студент ставит настоящий Python и работает в VS Code — песочница дальше не используется вообще, потому что не поддерживает `class`/`import` (нужны для ООП, стандартной библиотеки, pytest, requests, Selenium и т.д.). Вместо `check(out)` там два типа задач:
- **`kind:'checklist'`** — самостоятельно отмечаемый шаг на своей машине (поставил/запустил/закоммитил); опционально показывает код через `starter`, если его нужно ввести/скопировать
- **`kind:'predict', offline:true, expected:'...'`** — то же самое, что обычный `kind:'predict'`, но ничего не выполняется в браузере (сравнение идёт с заранее known-correct выводом настоящего CPython, не с рантаймом песочницы)

Оба типа уже реализованы в `js/app.js`. Весь новый код для таких модулей перед публикацией стоит реально прогонять через `python` (или наш `js/interpreter.js` для обычных модулей) — не считать «на бумаге».

**М14 (Selenium)**: навигация/чтение (`get`, `find_element(s)`, `.text`, `.get_attribute`, `NoSuchElementException`) реально прогнаны через настоящий Chrome против живого automationexercise.com. `.click()`/`.send_keys()` в этой конкретной песочнице (Claude Code sandbox) не работают — синтетический ввод через WebDriver блокируется на уровне окружения (подтверждено: JS-манипуляция DOM работает, `.click()`/`.send_keys()` — нет), это ограничение именно этой изолированной среды, не сайта и не кода. У реального пользователя на обычной машине эти вызовы работают штатно — это стандартный, учебниковый Selenium API, просто не был лично прогнан построчно в этой сессии.

**М15 (Playwright)**: в отличие от М14, здесь `.click()`/`.fill()` реально сработали в этой же песочнице (другой механизм синтетического ввода) — весь модуль, включая полный флоу поиска и `expect().to_have_text()`, прогнан end-to-end против живого сайта. Заодно нашли настоящую живую особенность сайта (не выдумка): cookie-consent баннер реально перехватывает клики (`intercepts pointer events`) на свежей странице — это стало отдельным заданием (т8) вместо того, чтобы быть незамеченным препятствием.

**М16 (архитектура фреймворка)**: финальный/капстоун-модуль собран и прогнан как реальный мини-проект — `pages/products_page.py` + `conftest.py` (yield-фикстура) + `tests/test_search.py` (Playwright) + `tests/test_api.py` (requests), всё вместе через один `pytest -v` из корня проекта. Порядок setup/teardown у yield-фикстуры и поведение `scope="module"` (setup один раз на файл, а не на тест) — оба подтверждены реальным прогоном с `-s`.

  - **✅ Уникальный силуэт-враг на каждый из 16 боссов** (`renderBossVisual`, 9 сентября 2026) — раньше все 16 использовали один и тот же жёстко закодированный SVG. Детерминированный генератор зубчатого силуэта (число зубцов/изрезанность/поворот + паттерн «глаз» + опциональный тематический акцент — мигающий курсор для окружения, прицел для локаторов, «цилиндры» для баз данных, нити марионетки для Playwright, двойник для моков, спираль для циклов/генераторов), сид от `moduleId` — стабильно между перерисовками. Проверено на все 16 модулей — каждый даёт свой уникальный path, чекпоинты корректно без босса.
  - **✅ Визуальный полиш боссов** (9 сентября 2026, запрос пользователя: «боссов тоже наверное покрасивее нужно оформить») — сама форма/уникальность силуэтов не менялась (тот же `BOSS_LOOK`/сид/детерминизм), полировка на уровне отрисовки: (1) `bossBlobPath` раньше соединял зубчатые вершины прямыми линиями (`L`) — читалось как рандомный зигзаг-каркас; теперь та же последовательность вершин обводится квадратичными кривыми через середины рёбер (вершина = control point, а не точка на самой линии — стандартный приём для «блоб»-силуэта) — силуэт стал гладким и выглядит как спроектированное существо, а не вайрфрейм, при этом форма для того же `seed` не изменилась, просто сглажена; (2) тело раньше было полой обводкой (`fill:none`, толстый `stroke-width:13`) — добавлена радиальная заливка-градиент (`radialGradient`, светлое коралловое ядро → тёмно-бордовый край, та же красная «вражеская» палитра, что и раньше у глаз/акцентов) поверх более тонкой обводки — даёт объём вместо плоского контура; (3) глаза были плоскими кружками — теперь у каждого мягкое красное гало (`opacity:.35`) вокруг светлого почти-белого зрачка (`#ffd9d3`) — читается как «светится изнутри». `id` градиента уникален на силуэт+статус (`bossGrad-${moduleId}${defeated?'-d':''}`) — на `#view-path` одновременно на экране до 16 таких `<svg>`, общий `id` заставил бы их все ссылаться на первый попавшийся `<radialGradient>` в DOM. Проверено: все 16 id уникальны на странице пути, обычный/повержённый режим оба используют новую заливку/глаза, консоль чистая, локально и на проде.
  - **✅ Превью босса на карточке модуля в пути** (`renderPath`, 9 сентября 2026) — маленькая версия того же `renderBossVisual(m.id)` теперь показывается справа на каждой карточке модуля в `#view-path` (третья колонка грида `.node`, `56px 1fr 64px`), заблёклая/чёрно-белая для ещё не открытых модулей. Заполняет реальное пустое место в карточке контентом («какой босс ждёт в этом модуле»), а не абстрактным декором. Скрыто на мобильной ширине (≤520px, третья колонка там не помещается).
  - **✅ Побеждённый босс визуально отличается от ещё не пройденного** (`renderBossVisual(moduleId, defeated)`, 9 сентября 2026) — реализован первый из двух вариантов, обсуждавшихся в этом пункте (сам силуэт босса выглядит иначе, а не сцена «герой побеждает босса»): при `state.completed[bossTaskId] === true` тот же детерминированный силуэт рисуется повёрнутым набок (`transform="rotate(65 100 100) scale(1,0.65)"`, `opacity:.55`), с крестиками вместо глаз, плюс приглушение через CSS (`.node-boss.defeated{opacity:.6} .node-boss.defeated svg{filter:drop-shadow(...) saturate(.6)}`). Применяется в двух местах: превью на карточке модуля в пути (`renderPath`) и боссовый хедер (`renderBossHeader`, там же тег меняется на «BOSS DEFEATED»/«БОСС ПОВЕРЖЕН», health-бар — на символические 4% вместо декоративных 68%). **Отдельно найденный и пофикшенный баг:** сразу после победы (без выхода из модуля) хедер не обновлялся — `runCheck()`/`runPredictCheck()`/чеклист-обработчик патчили только карточку конкретной задачи, `showVictory()` показывала оверлей, но сам `renderBossHeader` за оверлеем оставался в позе «жив» до следующего открытия модуля. Добавлен `refreshBossHeader(t, m)` (полная перерисовка `.boss-header` через `outerHTML`), вызывается в паре с `showVictory(t, m)` во всех трёх местах, где та вызывается. Проверено: обычные и checklist-боссы, обновление мгновенное, вид после F5/повторного входа совпадает с видом сразу после победы.
  - **✅ пофикшено** — «чёрная линия слева» у боссового хедера, которая осталась ПОСЛЕ того, как сама карточка и ряд иконок уже были поправлены (два предыдущих фикса). Причина оказалась в третьем, ещё более глубоком слое: `.arcade-linebg`/`.arcade-glow` по умолчанию `inset:0 0 0 38px` — те самые 38px зарезервированы под `.arcade-gutter` (колонку номеров строк) на титульном/victory-экранах, но `renderBossHeader()` эту колонку не рисует вообще, поэтому фоновый паттерн не доходил до левого края, оставляя видимый шов. Добавлено `.boss-header .arcade-linebg{ inset:0 }`. Урок подтверждает вывод из предыдущей записи выше: у одной и той же жалобы «пусто/что-то не так слева» было целых ТРИ независимых причины на разных уровнях вложенности (ширина карточки → выравнивание иконок внутри → отступ фонового паттерна ещё на уровень глубже), каждую пришлось находить измерением, а не предположением.
